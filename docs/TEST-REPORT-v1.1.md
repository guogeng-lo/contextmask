## 隨機測試

隨機把不同寫法的設定組在一起，每段之間穿插普通的程式碼、空行、註解，有時候整段加上縮排，有時候換行改成CRLF。虛構密碼中間會隨機夾0到4個特殊字元，字元依寫法挑選那種寫法本來就允許的（例如雙引號裡不放`"`和`\`，命令列不放空白和引號）。每一組都檢查：遮罩後直接還原和原文一字不差、換行和縮排不變，而且每個虛構密碼都要整段落在某個代號換掉的內容裡，只遮到一部分也算失敗。種子固定（預設20261010），失敗的話可以重現。

- 隨機測試A：只用支援的48種寫法（加了Codex補測的三類），20,000組裡每種寫法至少出現1,769次。結果每個虛構密碼都整段遮住。其中11組多列了「沒遮完整」：都是隨機縮排剛好把後面幾段排到`password:`的清單底下，變成敏感名稱底下的物件，照D04列為要確認，算是保守的結果。
- 隨機測試B：再加上7種沒辦法完整遮的寫法（找不到結尾的三引號、看不出範圍的路徑、找不到結尾的引號、大寫環境變數後面還有一段值、`secrets`底下的`db`、JSON`secrets`底下的`note`字串，以及R09的換行沒縮排JSON），20,000組裡每種至少出現1,557次。有8,609組有值沒遮完，全部都有列為沒遮完整、要確認。
- 另外換兩個種子（99、4242）各跑100,000組，A、B兩項都通過（A多列「沒遮完整」的各有93組和102組，原因同上；B沒遮完的各有43,022組和42,959組，全部都有列出）。

`npm test`預設跑的是5,000組，結果一樣全部通過（數字在`npm-test.txt`）。

## 效能

這是在Node.js裡量的核心時間（掃描加遮罩），不包含畫面，也不代表手機上的速度。

- 99,428字、938筆候選的錯誤訊息，量了5次：25.2、14.7、16.9、16.7、24.9 ms（`perf-5runs.txt`）。同一台機器每次量的結果會差幾ms，拿修改前的`index.html`量也一樣會跳動。目標是2秒內。
- v1.0原本的36種特殊輸入（長串同一個字元、大量符號、重複的欄位等）都在2秒內。
- v1.1新增的48種特殊輸入（沒有結尾的括號、一直換行的欄位、沒關上的三引號、很多層的函式呼叫、很長的格式化字串、換行的呼叫參數、很多層的敏感物件，以及這次加的2萬行註解、1萬4千行的敏感物件、9萬9千行空行，和R09加的每行一個沒縮排的`"secrets":{`等）都在2秒內。最慢的是一直重複`{"secrets": {`、沒有結尾的輸入，在整份測試裡量到約0.8～1.2秒（每次跑不太一樣）；同一份測試拿修改前的`index.html`跑也是約1.1秒，單獨量這一項約0.3～0.4秒，所以看起來是跟在新加的輸入後面量造成的，不是這次的修改。離2秒的目標比上一輪近，之後如果再加規則要注意。
