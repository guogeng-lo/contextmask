# ContextMask討論跟修改紀錄

2026-10-10

（這份前面是做v1.1之前記的；最後一段「v1.1做完之後」是我操作回饋和Codex測試審查之後補的。實際改了什麼見《ContextMask修改紀錄v1.1》。）

我先把這次自己用過之後的感覺記一下。目前主要是在確認哪些地方需要改，還不是新版全部做完了。

介面這邊（D02），我覺得可以自己決定哪些內容要遮住，這點不錯。我貼出的結果裡，原本的USER_1沒有被換掉，路徑用了USER_2，另外也有student_number = SID_1。不過畫面看起來有點雜，雖然有提醒原文本來就有USER_1，使用者還是可能漏看，就不知道為什麼會從USER_2開始。還原那邊也是一樣的感覺。

雖然使用者可能是資工學生或有相關知識的人，我還是希望門檻低一點，最好不用一直找說明才知道在幹嘛。

後來討論了保留對照畫面、把細節收起來，或是改成一步一步操作。其實兩個都不錯，不過我比較偏向第一個，因為我希望操作不要太麻煩，也不要增加太多限制。畫面盡量乾淨，但是提示又要讓人看得到、記得住。

這個也不用大改，我覺得可以參考其他工具怎麼排，小修一下就好。主要是讓使用者更快上手理解，不是要整個重新做。

代號的部分也一起記在這裡（D01）。我選USER_1這種短代號，當然主要就是包括我在內的使用者可以更容易讀。只是程式裡本來就可能有USER_1，所以我決定先找出原文已有的代號，新的跳過它，從USER_2開始。還原只換這次發出去、有對照資料的代號，原本的USER_1不動。像USER_9這種對照表沒有的，就列出來，不要自己猜原本是什麼。

還有密碼的提醒（D03）。討論到密碼還在、畫面檢查卻通過的情況，我確實會直接複製給AI。這部分就讓我覺得，提示需要再清楚一點，要讓使用者知道哪裡有問題，處理之後能比較有把握地複製。

AI原本比較建議遇到沒處理完整的敏感欄位就先擋複製。我最後選的是「醒目提示風險，使用者確認後仍可複製」，這也跟前面希望不要太多限制的方向一致。不過已經找到的漏遮還是要修，不能只是多放一句提醒就算好了。

AI後來把這個選擇補成比較具體的規則：沒處理完整的欄位要在複製附近看得到，讓使用者可以先修改或補遮罩，也可以確認風險後繼續。確認不能先幫使用者勾好，也只算這次的結果；改了原文、關鍵字或審查選項，或重新掃描、產生結果，就要重新確認。確認完也還是保留提醒，不要突然變成看起來全部安全了。

另外，不能正確還原或原本有效的JSON被弄壞，這些還是照規格擋下，不能用上面的確認跳過。正常沒有問題的流程，就不要再加一次確認。

這次我做的是親自操作、提出哪裡容易漏看，還有選擇我想要的處理方式。AI幫忙提出不同方案、整理文字，以及把決定變成規格跟測試條件。我提出介面調整和查錯的要求，程式修改主要交給AI。前面AI跑的技術測試跟我自己的使用感受分開記，不能算成都是我測的。

現在這幾個方向已經選好了，實作跟新版驗收還沒做。等新版完成，我再用相同例子看一次，確認提示有沒有真的比較好懂，操作會不會反而變麻煩。

## v1.1做完之後

新版做好之後，我繼續用使用者的角度操作，看看提示懂不懂、流程順不順，也請Codex幫忙測試查錯。75＋43項核心測試、隨機測試A和B各20,000組，還有重新建出HTML比對檔案，都是Codex執行的。跳號說明、還原摘要、D03的確認跟重設、JSON阻擋，也由Codex另外在畫面上檢查。我做的是基本操作和使用體驗回饋，沒有親自跑這些大量測試。

Codex依我的查錯要求另外補測，找到三類漏遮：呼叫的密碼參數換行、YAML欄位名稱加引號之後的延續行，還有`config[ "password" ]`中括號加空白。問題是Codex找出的，我要求把這些問題修好再公開，不要帶著已知的漏遮上傳。

操作的感覺（A41）：跳號說明和還原摘要有比較好懂，操作也還行，入門的人應該也會用。不過下面的「支援哪些寫法、有哪些限制」可以醒目一點，我自己當使用者看了一下，還真不一定會滑到下面點開來看；查看要複製的完整內容跟其他地方也一樣，比較重要的資訊使用者不一定會點開或特別注意。我認為要多加引導，讓使用者能更確定、更安心地把內容複製給AI，確保隱私。

我提出要再調整的地方：最上面直接寫找得到和找不到什麼、複製按鈕上面加「送出前再看一次」、選了保留的那一筆直接顯示風險。介面、中括號空白和另外兩類漏遮的程式修改，主要由Claude完成，D04物件範圍的判斷和大量自動測試也是AI處理。我負責說明問題、選擇處理方向，並從使用者的角度看操作有沒有比較好懂。

另外是敏感欄位底下的物件（D04），例如`secrets:`底下的`db: abc`。我建議這版保留逐欄位遮罩，再對這種物件加上D03的確認，比較符合希望保留除錯線索、操作又不要限制太多的方向。我會這樣選有三個理由：`credentials`裡可能同時有帳號、密碼和設定值，全部遮掉會少掉除錯線索；`secrets`已經是明確的風險線索，應該在畫面上提醒，不能只寫進規格的限制；這版先把提示和確認做好，範圍比較能控制，「依父層判斷所有子欄位要怎麼遮」之後再做。

總之這輪我給自己一句重點：把使用者當成白癡去設計吧！（半開玩笑的原話。寫進規格書和README的時候，我改成「把使用者當成什麼都不會的人來設計」，意思一樣，只是沒那麼衝。）

講出來之後回頭看，其實前面D01到D04我一直都是這樣在想：代號要好讀、跳號要講清楚、門檻要低、風險要擺在眼前但不要限制太多、除錯線索要留著。只是到這輪自己當使用者，才把它變成一句話。

## 補充審查之後

我又請Codex審查一次，找到兩個D04的確認缺口：`secrets`裡保留中文、符號這種字串時沒有確認框，還有超過200行的物件只看前面就放行。這兩個我覺得一定要修，既然已經知道`secrets`是風險線索，就不能因為內容看起來不像密碼就讓它直接過去，沒檢查完的也不能當成檢查過了。

另外我想到，如果我是一個懵懵懂懂的新手，第一次看到這個畫面可能會不知所措。所以我要求在最上面加5個步驟的說明，像之前Claude教我操作步驟那樣，該看哪裡、該點什麼、要注意什麼、什麼能給AI，都直接寫出來。這也是同一個原則，使用者不一定會自己摸索，那就直接告訴他。

改好之後我用了最新版，確實都有照我的需求改，現在應該所有人都會用了，果然什麼都不會的人也能用吧。雖然有點擁擠，第一次點進來可能會被大量文字嚇到一點，但至少都有引導，應該不至於不知所措，希望大家不會沒耐心看。之後如果要精簡文字，也要先找新手試用，不能為了好看又把重要的提示收起來。

上傳前我又請Codex最後驗收一次，結果還是抓到一個R09：JSON換行但沒縮排時，`secrets`裡沒遮的值不會要求確認。單行或有縮排的都沒問題，偏偏就這種寫法漏掉。測試全過也不代表沒問題，所以我的判斷一樣是修好再上傳，不要帶著已知的洞公開。

修好之後我自己在電腦和手機上用Edge、Chrome、Brave都試過，都能用。我自己用是沒問題，但我是做這個工具的人，本來就知道要怎麼操作，都說旁觀者清，之後還是要找別人實際用用看才準。
